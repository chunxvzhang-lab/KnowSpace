### 1.2 数据模型（`core/types.ts:9-27`）

`MindmapNode` 是**严格树**：`children: MindmapNode[]`，无 `parentId`、无 `isFloating`。

已有属性：`text` · `level` · `line` · `collapsed?` · `color` · `shape` · `lineColor` · `lineStyle` · `fontSize` · `fontWeight` · `textColor` · `borderColor` · `textAlign` · `customWidth` · `customHeight`

**未实现**：备注 · 图标 · 标记(marker) · 标签 · 超链接 · 图片 · 编号 · 字体族

### 1.3 持久化通道（**这是全案的关键约束**）

导图**没有独立文件格式**，唯一持久化方式是把结构写回 Markdown：

| 内容 | 编码方式 |
| :--- | :--- |
| 层级 | 标题 `#` 数量，或列表缩进深度 |
| 顺序 | `children` 数组顺序 |
| 样式 | **行尾 HTML 注释** `<!-- style: color=#10b981,shape=capsule -->` |
| 块引用 | 原有 `^block-id` 保留 |

同步算法 `syncMindmapToDocument` 按**章节（标题块）对齐**，正文段落/代码块/表格/公式**整段搬运**。

### 1.4 已确认的功能缺口（勘定结论）

| 维度 | 缺口 |
| :--- | :--- |
| **结构** | 无自由主题 · 无关系线 · 无概要 · 无边界 |
| **布局** | **仅 1 种**（右向水平树）；无径向 / 双向 / 逻辑图 / 时间轴 / 树状表 |
| **主题** | **无主题概念**（`theme` prop 仅用于 PNG 判定深浅底）；8 色自动分支配色 + 手工选色 |
| **节点内容** | 仅纯文本（无备注 / 图标 / 标记 / 标签 / 链接 / 图片 / 编号） |
| **编辑效率** | 无复制粘贴剪切 · **无同级拖拽排序** · 无框选 · 无空白双击新建 · 无画布右键菜单 |
| **视图操作** | 无缩放快捷键 · **无一键适应画布按钮**（仅挂载时自动执行一次） |
| **状态持久化** | 折叠态 · 缩放态 · 撤销栈**均不持久化** |
| **导入** | **完全没有**（OPML / FreeMind / XMind 均无解析器） |

### 1.5 勘定中发现的既有瑕疵（顺手可修）

1. `reparentNode` **已有 `targetIndex` 形参**，但 UI 调用时**不传** —— 所以拖放一律追加为最后一个子节点。**同级拖拽排序的实现成本因此极低**。
2. `MindmapNode.collapsed` 字段**只被读不被写** → FreeMind 导出的 `FOLDED="true"` 永不生效。
3. `MindmapView.tsx:31,47` 两个**死导入**（`mindmapTreeToMarkdown`、`MindmapLayoutNode`）。
4. `styles.css` 中 `.mindmap-node-add-btn` 等**遗留样式**（JSX 已不渲染，且有测试断言其不存在）。

## 2. 核心架构决策（**必须先拍板，否则后面全是返工**）

XMind 的模型是**自由图 + 富节点元数据**；KnowSpace 的模型是**Markdown 文档结构的投影**。两者不是同一种东西，直接堆功能会撞上根本矛盾。以下三个决定是后续一切工作的前提。

### 决策 1 · 富节点元数据（备注 / 图标 / 标记 / 标签 / 超链接 / 图片）存哪里？

| 方案 | 做法 | 代价 |
| :--- | :--- | :--- |
| **A** | 继续扩展 `<!-- style: -->` 注释 | 注释会变成一行 JSON，**Markdown 可读性崩塌**；正文被污染 |
| **B** | 全部搬进 sidecar 文件 | 结构也一起走 → **放弃「Markdown 是结构事实源」这一核心优势** |
| **C** ✅ | **结构 + 样式继续在 Markdown；富元数据进 sidecar** | 需要新增一个伴生文件与同步规则 |

> **推荐 C。** 理由：Markdown 保持「打开任何编辑器都能读懂结构与基本样式」，而备注、图标、标记这类**在纯文本里本来就表达不了**的东西，不该硬塞进注释。
>
> **伴生文件**：`<文档名>.mindmap.json`（与文档同级，仅在该文档确实用到富元数据时才创建 → **不用的人完全看不到它**）。

### 决策 2 · 非树形结构（自由主题 / 关系线 / 概要 / 边界）如何表达？

| 方案 | 做法 |
| :--- | :--- |
| **A** | 坚持纯树，不支持 |
| **B** ✅ | **支持，但只存在于 sidecar** —— 树仍是 Markdown 的投影，自由主题与关系线是**附加层** |

> **推荐 B。** 这保住了两条性质：① Markdown 仍是结构事实源；② 导图能表达 XMind 的图结构。
>
> 具体：自由主题 = 无父节点的顶层节点；关系线 = `{fromId, toId, label?}` 列表；概要/边界 = 任意节点 id 集合 + 样式。**全部只写 sidecar。**
>
> ⚠️ 需明确记录：**导图 → Markdown 写回时，附加层不受影响**（同步只处理树）。

### 决策 3 · 主题（换肤）如何落地？

| 方案 | 做法 | 代价 |
| :--- | :--- | :--- |
| **A** | 切主题时把样式**写进每个节点** | **破坏性** —— 会覆盖用户手工调过的样式，且切回来无法还原 |
| **B** ✅ | **主题 = 视图层默认值；节点显式样式优先** | 需要区分「节点显式设置」与「继承默认」 |

> **推荐 B。** 「未显式设置样式的节点」跟随主题；手工设置过的节点保持不变 → **换肤瞬时且非破坏性**。
>
> 实现要点：主题只影响 `layoutMindmap` 的**默认值来源**（现在硬编码的 `BRANCH_COLORS`、默认字号 15/13、默认形状等），不改写 markdown。

## 4. 建议的执行顺序与理由

```
M0（交互补齐）  ← 立即可做，无模型风险，用户感知最强
   ↓
M1（主题体系）  ← 无模型风险，视觉提升显著
   ↓
M2（布局切换）  ← 无模型风险，纯布局函数
   ↓
─── 评审点：决策 1 / 2 拍板 ───
   ↓
M3（节点富元数据） ← 需要 sidecar
   ↓
M4（非树形结构）   ← 需要 sidecar
   ↓
M5（导入导出）
```

**为什么 M0 排第一**：勘定显示**五项最影响手感的交互全部缺失**，而它们**完全不碰数据模型** —— 复制粘贴、同级拖拽排序、框选、空白双击、画布右键菜单。其中「同级拖拽排序」的 `targetIndex` **参数早就存在，只是没传**。

**为什么 M3/M4 必须等评审**：它们决定**是否引入 sidecar 文件**，这是**产品形态层面的选择**（用户会不会在文件夹里多看到一个 `.mindmap.json`），不该由我单方面决定。

## M0.7 折叠状态持久化 —— 实现前的两项核实

> 记录于动手之前。这一节只写已经**核实过的事实**和**尚未解决的问题**，不含实现。

### ✅ 核实一：节点 id 跨重载稳定，按 id 持久化是有效的

持久化折叠状态最自然的做法是存节点 id 的集合。这只有在 id 稳定时才成立 —— 若 id 每次解析都重新生成，存下来的集合会在重载后全部落空，而且**单元测试测不出来**（测试里 id 是固定的）。

核查 `parseMarkdownToMindmapTree` 的生成规则：

| 节点来源 | id 形式 | 稳定性 |
| :--- | :--- | :--- |
| 根节点 | `root-mindmap-node` | ✅ 固定字面量 |
| 缩进列表项 | `node-${parentPath}-${childIdx}` | ✅ 由**结构路径**派生 |
| Markdown 标题 | `heading-${line}-${text.slice(0,10)}` | ✅ 由行号与文本派生 |
| **新建节点** | `node-${Date.now()}-${random}` | ⚠️ 随机，但仅存在于当前会话 |

最后一行不构成问题：新建节点在同步回 Markdown 后，下次解析会重新获得**结构 id**。随机 id 是会话内的临时标识。

**结论：可以按 id 持久化。**

> ⚠️ 已知局限（非本次要解决）：id 含**兄弟序号**。若在折叠的节点之前插入同级条目，其序号改变、id 随之改变，折叠会落到错误节点上。这是序号路径的固有代价，换用文本路径可解但会引入重名问题 —— 记为已知取舍。

### ⚠️ 核实二：组件拿不到文档标识，需要一个新 prop

`MindmapViewProps` 现有字段：

```ts
title: string;
headings?: Heading[];
source?: string;
onSourceChange?: (newSource: string) => void;
editable?: boolean;
onJumpToHeading?: (headingId: string, line?: number) => void;
onClose?: () => void;
theme?: ThemeMode;
```

**没有文档路径。** 而持久化的键必须是**每文档一份**。

| 方案 | 评价 |
| :--- | :--- |
| 用 `title` 作键 | ❌ **已知错误** —— 同名文档（如各目录下的 `README`、`索引`）会共用一份折叠状态 |
| 新增 `documentKey?: string`，由 App 传入路径 | ✅ 正确，且 App 已有 `session?.absolutePath` |
| 存进文档自身（frontmatter / 注释） | ✅ 随文档走，但要处理「同步时不写脏」的问题，且会**改动用户的文档** |

**倾向第二个**：不动用户文档，键正确，改动面小（App 一行、组件一行）。

### 径向布局（M2.3）的三处要点

**扇区权重是混合的，不是纯按体量。** 纯按体量分配听起来对，但它会坏：一个只含单个叶子的分支挨着一个大分支时，它的扇区趋近于零宽，而**两个框不重叠所需的半径 = 框宽 ÷ 角间距** —— **整环会被推到几千像素之外**。混合 50% 的均分把最窄扇区**限制在父扇区的固定比例**，重的分支仍然明显更宽（测试里 5:1 的体量比变成不到 3:1）。

**环半径由两条约束取大**：① 上一环半径 + 两环各自的最坏径向半宽 + 间距；② 本环相邻框的角间距反推出的最小半径（**首尾也算相邻 —— 环是圆不是线**）。

**连线的三种形状按半径旋转**：`step` = 沿父方向出到中间环 → 弧上横移 → 到子节点；`bezier` 用同样两点作控制点；`straight` 就是辐条。中间角取**最短弧**，否则刚好跨过起点的分支会绕大半圈。

**折叠按钮**：径向节点的子节点分布在四周，"在哪条边上"没有答案，因此布局节点新增 `toggleOffset`（节点本地坐标的落点），渲染器优先用它，其余布局仍走 `side`。**这也顺手解决了时间轴问题的一半。**

### M1.4：主题体系的逃生口

主题是**默认值来源**：没设样式的节点跟随主题 —— 这是"换肤瞬时且非破坏"的全部依据。代价是**想"以主题的答案为起点、再手工调一个节点"的人无从下手**，因为那个答案从来没有写进节点。

**固化就是补上这一步**：把当前主题解析后的外观写成这些节点自己的样式，此后它们不再跟随主题。

**它不覆盖任何东西。** `resolveNodeAppearance` 本来就**优先节点自己的值**，所以把解析结果写回去，对节点已经设过的每个字段都是**无操作**。因此这里的确认说明的是「**钉住**」而不是「**会丢失什么**」—— 这条直接写进了函数的注释里，因为把确认文案写对的前提是先想清楚它。

**落点**：节点样式面板的动作区，与删除并列 —— 两者都是"对节点的决定"，而不是"对节点的控件"。批量选中时同样可用；**确认由视图层负责**，面板保持纯展示。

### 布局切换的落地方式

**布局是纯视图层选择**：`layoutMindmap(tree, collapsedIds, layoutId)` 只返回坐标与连线路径，不改树、不写文档、不动节点样式。切换布局 = 重新算一次坐标。

**新增的共享结构**（三个布局共用，避免各自漂移）：

| 函数 | 作用 |
| :--- | :--- |
| `makeLayoutNode` | 由树节点 + 位置装配布局节点。**三个布局共用一份字段清单** —— 否则将来给 `MindmapNode` 加一个样式字段，就会漏掉其中一两个布局 |
| `measureSubtree` / `measureSubtreeWidth` | 纵向 / 横向的子树占位（互为转置） |
| `stackHeight` / `stackWidth` | 一排兄弟占用的高度 / 宽度 |
| `shiftToOrigin` | 布局完成后整体归位到原点（左右两侧的伸展只有在排完后才知道） |
| `buildEdgePath(…, axis)` | 连线形状按轴旋转：`step`/`bezier` 原本假定"从左往右流"，直接用在纵向布局上会**横向穿过下一层** |

**新增字段** `MindmapLayoutNode.side`：`right` / `left` / `bottom`。折叠按钮挂在**子节点实际所在的那条边**上；默认布局全是 `right`，所以旧观感没有任何变化。

### 时间轴（M2.5）：方案 ① 可行，但只有一条路

**先否掉了看起来最直接的做法**：从根**直连**分支 —— 直线、`step`、`bezier` 都会**穿过中间的分支方框**。轴是水平的、分支沿轴排开，连向第 5 个分支的线必然掠过前 4 个。

**唯一可行的路是"沿轴走，再垂到节点"**，它成立的前提是：**轴是唯一没有被方框占用的走廊** —— 所有方框按构造都退到轴的一侧至少 `SPINE_GAP`。也正因为这条走廊，**分支必须上下交替**：全放一侧就没有走廊可言了。

**由此得到一条渲染决定**：轴上的每一段**共线且重叠**，若各用各的分支色，靠近根的一段会混成脏色、到远端才渐渐变成单色。因此**轴上的所有段共用第一个分支配色**；分支自己的颜色留在它的节点与子树内部的连线上。

**`side` 增加了 `top`**（时间轴的上侧分支朝上生长）。径向那种"哪条边都不是"的情形仍由 `toggleOffset` 表达 —— 两种机制各管一种"方向不是一个名字"的情况。

**验证**：有一条测试专门断言「**轴上的那段走廊没有任何方框占用**」—— 这是整个设计的支点，它一旦被推翻，时间轴就得改成方案 ②（把主轴提升为渲染概念）。

### 性能实测（方案 §5 风险表里唯一未验证的一条）

方案写着「大图（>500 节点）需实测」。实测两种形状：

| 形状 | 逻辑 | 双向 | 纵向 | 径向 | 时间轴 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| **841 节点 / 3 层**（宽而浅） | 3ms | 3ms | 6ms | 2ms | 1ms |
| **601 节点 / 600 层**（深链，最坏） | 94ms | 124ms | 80ms | **5ms** | 80ms |

**结论：不需要优化。** 真实文档落在第一行的量级上。

**但两行的差距说明了一件事**：每个布局都靠**遍历子树**来回答"这棵子树有多高 / 多宽"，于是一条深度 d 的链要付 d² 次访问 —— 宽树把这份代价完全藏住了。**径向快 20 倍，只因它在第一阶段就把每个节点的尺寸算好、存进条目里复用**，其余四个布局每层都要重算一遍。

> **为什么记录下来而不是顺手优化**：600 层不是任何真实文档的形状，为一个不存在的场景去改四个布局的度量路径，等于**把风险挪到用户真实会走的路径上**。真遇到深文档卡顿，这就是第一个该改的地方。

### ⚠️ 性能测试的断言改过一次：**断言次数，不断言时间**

墙钟上限试过，但它**没活过自己所在的套件**：深链单跑 771ms，62 个文件并行时 **6599ms** —— 那个上限量的是**机器有多忙**，不是代码有多慢。**一个节点被度量多少次，与旁边在跑什么无关**，而那正是代价的构成。

| 形状 | 逻辑 | 双向 | 纵向 | 径向 | 时间轴 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| **841 节点 / 3 层**（度量次数） | 4962 | 5762 | 4121 | **841** | 3281 |
| **601 节点 / 600 层**（度量次数） | 36.2 万 | 54.2 万 | 36.1 万 | **601** | 36.1 万 |

**宽图的天花板定在每个节点 10 次**（实测 3.9–6.9 次）—— 一条"每个节点都重走整棵树"的改动会是它的四十倍。

**深链那条不做断言、只打印**：它按构造就是平方级，任何阈值都是拍出来的数字；它存在的意义是让**两行相差三个数量级**这件事可见。

> ⚠️ **顺带一条工具教训**：这条测试还撞上过 **Vitest 默认的 5 秒超时**（并行时 7.9s）。**故意偏重的用例必须显式给超时** —— 否则它失败的样子看起来像断言挂了，而实际上只是排在了队尾。

### 导出 SVG：一个函数，两种格式

**PNG 导出本来就要先把画布序列化成一份"独立 SVG"再栅格化**，所以 SVG 导出**不需要第二套实现** —— 把那段逻辑抽成 `services/mindmapSvgExport.ts`，PNG 继续拿它去栅格化，SVG 直接把它写进文件。

**共用是刻意的**：两种格式如果各写一份，"某个节点的填充怎么解析"这类修复就会只落在一种格式上，而**两种格式的差异恰恰是那种要等用户拿到一个坏文件才会被发现的问题**。

**它要解决三件事**（各有一条测试）：把平移缩放解掉（那是读者的位置，不是图的一部分）；去掉只属于交互的元素（选择框、添加按钮、缩放手柄）；把来自样式表的颜色落成字面色值（样式表不随文件走）。

**测试还真抓到一个我自己引入的缺陷**：模块里手工设了 `xmlns`，而序列化器**本来就会写它** —— 结果属性出现两次，**那不是合法 XML**，严格的解析器会直接拒绝文件。已改为不手工设置，并用一条断言钉住"命名空间存在**且只有一个**"。

> 附带一条事实：节点自设的颜色经 CSSOM 读回来会变成 `rgb(255, 0, 0)` 而不是 `#ff0000`。**颜色一样、文件也合法**，但测试的预期要按事实写，不能按直觉写。

### M5.1b：打印即 PDF

**没有写转换器。** 应用已有 `printToPdf`（主进程）与整套 A4 打印样式表，文档的 Ctrl+P 走的就是它 —— 导图复用它，**新依赖为零**。

**要补的是"整张图适配纸张"，原来缺的一半在样式表、一半只能在代码里**：

- **样式表**（`@media print` 内新增一段）：解除平移缩放（`transform: none`）；画布按宽度铺满、高度封顶一页 —— `preserveAspectRatio` 默认 `meet`，所以**过宽或过高的图会被整体缩小而不是被裁掉**；隐藏与 PNG / SVG 导出一致的那批控件。
- **代码**（`MindmapView` 里打印前后设置与复原 `viewBox`）：**`viewBox` 只能由代码给出**，它取决于布局算出的边界，样式表拿不到。监听浏览器与 Electron 打印时都会触发的 `beforeprint` / `afterprint`。
  - 复原值**在打印发生时读取**，而不是在 effect 建立时记住 —— 否则第二次打印会把第一次装上去的值当成"原值"。两条都有测试：视图框换入换出、**连续打印两次也收得回来**。

**一个前提值得写明**：导图是**替换阅读区**的独立视图（`viewMode === "mindmap"`），所以打印导图时纸上只有导图，不会顺带印出文档。

**M0–M2 与 M5.1 都还没有引入任何新文件格式**：五个布局、主题、交互、四种导出全部只作用于视图层或复用既有通道，所以这些里程碑都能随时停下而不留半成品。**sidecar 会是第一个新格式**，这也是它值得单独拍板的原因。

### M3.3 完成：优先级与进度（方案里的"标记"收窄了范围）

**先说范围上的改动**：方案原本把"标记"定为 *优先级 1-9 / 进度 0-8 / 星标 / 旗标*，但**星标与旗标已经被 M3.2 的图标表覆盖**（`star` / `flag` 就在"重点"组）。再做一个平行的"标记组"会让同一个概念有两个入口，所以这次只做了**图标表达不了的那两样**：**优先级 1–9**（数字角标）与**进度 1/8–8/8**（扇形表盘）。这是产品形态上的取舍，记录在此以便推翻。

**没有 0「进度」**：0/8 是一个什么也没说的标记，等价于"没有标记"；选择器用"空着"来表达这件事，而不是画一个空圈。

**为什么标记是一段而不是两段**：`markers` 的形状是 `节点 id → 小对象`，因为**一个节点可以同时戴优先级和进度**。若拆成两个数字映射，同一个节点会在两处各占一个键 —— 而"一个节点一个键"正是这份文件其他段落都在用的形状。

**越界值：丢掉或清除，绝不夹取（clamp）**。手改过的文件或来自更宽刻度的版本可能写着 `priority: 12`；把它"顺手"改成 9，等于**替读者下了一个他没下过的判断**。清除只影响**自己那一项** —— 越界的进度不会连优先级一起带走。

**同一条规矩再往下一层**：条目标里**不认识的字段照样保留**（例如 `{"priority": 1, "review": "pending"}`），与"不认识的段落原样写回"是同一条规矩在两级上的落地。

**表盘的几何是被测过的，不是调出来的**：14 像素下画错表盘和画对表盘长得几乎一样，所以测试直接断言**边缘点落在圆上**、**角度等于这一格**（十二点起顺时针）、**大弧标志在过半时为 1**、**扫掠方向恒为 1**。为此把路径算法放进了核心表（纯函数）而不是留在组件里。

**画在哪里**：进度与优先级画在**节点框之上、右上角**，理由与图标一致 —— 节点尺寸属于布局，为标记撑大框会移动整张图。

**两条测试是我自己写错的**（都被实现纠正过来，值得记一笔）：①我以为"越界的进度"应该把整个节点标记清空，实现只清它自己那一项 —— 实现是对的，测试改了；②路径断言里我手数 token 下标，漏算了 `M` / `L` / `A` 这些字母，于是断言读到了 `"A"` —— 改成按名字取弧标志。**第二处尤其说明问题：手数下标写出来的断言，会以"通过"或"失败"任一方式骗人。**

### M3.4 完成：标签（以及承诺过的"第四种形状"复盘）

**先兑现承诺：加第三种形状（`tags`）之前回头看那套 `KNOWN_SECTIONS`，结论是保留、但把判断写进注释。** 理由：**只有"读"是按形状定制的**，而"空就省略 / 是否全空 / 不认识的段落带过去"三件事本来就与形状无关。四种读法各自类型与规则都不同（字符串映射、对象映射、数组映射），把它们塞进一张"描述表"只会让四个不同的函数共用同一个签名，买不到什么。**所以留下"名字列表 + 按形状的读函数"，并写明：再出现一种形状（日期、带标签的链接、嵌套列表）时，该换的是这套做法本身，而不是再加一个名字。**

**标签的规则（这是这次真正要定的事）**：

| 规则 | 理由 |
| :--- | :--- |
| `#` 是装饰，存进去之前剥掉 | 否则会同时存在 `api` 与 `#api` 两枚标签 |
| 按 `,` `，` `、` 与空白切分 | 只认一种分隔符，会把后面整串静默变成一个标签 |
| **大小写不同算同一个**，留下**先写下的那个拼法** | `#API` 与 `#api` 是一枚标签；全部转小写虽整齐，却会毁掉 `#KnowSpace` 的写法 |
| **读取时过同一套规则** | 手改过的文件不该能塞进一个面板自己会拒绝的标签 |
| 建议芯片 = **本文档在用的词表** | 用过的词最可能是下一个要用的，这也是"同一件事两个名字"长不出来的原因 |

**画在节点下方**（仍是"框外"，节点尺寸归布局管）：最多 **3 枚 + `+n`** —— 一张图上挂二十个标签就不是图了。芯片里的文字只为**绘制**截断（18 字符），文件里永远是读者自己的拼法。

**面板里唯一的一处状态**：标签输入框的值不是"存的东西"，而是它的**解析结果**。若由解析结果反向控制，刚打下的分隔符会被立刻吃掉（`api ` 变回 `api`，下一个词就粘上去了）—— 所以草稿留在输入框里，**并把节点 id 一起记住**，这样切换节点时半途写的字不会跟过去。回车与失焦都提交。

**平手时按"首次出现"排，不按名字**：`localeCompare` 会把顺序交给 locale，同一份数据在两台机器上给出不同顺序，而读者看不出任何理由。

**这里又踩了一个测试自己的坑，值得点名**：我的 `nodeIdOf` 只在一级子节点里找，找不到就**静默退回第一个子节点** —— 于是两个标签写进了同一个节点，一条本该失败的断言看起来通过了。**修正方式不是"再试一次"，而是：找不到就抛错，并且真的搜整棵树。** 静默兜底会把错误伪装成通过。（这已是 M3.3–M3.4 里第三次"实现是对的、测试是错的"，前两次是越界清除与手数 token 下标。）

### M3.5 完成：节点链接（M3 到此收口）

**三种形式，加一个"第四个答案"**：`https://…`（交给系统打开）、`[[文档]]` / `[[文档#标题]]`（交给阅读器那套解析器）、`#标题`（本文档内跳转）。**读不懂就返回"不是链接"，而不是猜** —— 裸文本 `产品设计` 不算链接（本应用的内部链接写法是 `[[…]]`，猜的话打错字就会跳走），`[[文档|别名]]` **也判为读不懂**：把竖线前那段当成文档名，会把人送去一个他从没提过的文件；面板会说清"不是可识别的链接 + 可用的三种写法"。**原样存下**这一版读不懂的写法，留给读得懂的版本 —— 这正是"存原文而非存解析结果"的理由。

**画布上的标记只给认得出的链接**：徽标的意思是"这里能去别处"，**为去不了的文字挂一个徽标，就是这张图上唯一的一处谎话**。读不懂的文字仍然在面板里显示（连同提示），没有任何东西被藏起来。

**跟随走的是三条既有通道，没有发明第四条**：外壳的 `openExternal`、阅读器的 `onWikiLinkClick`（**App 里已有 `handleWikiLinkClick`，接的是同一个** —— 一个"这个名字是哪个文件"的答案，不是第二个可能与之矛盾的）、以及标题跳转 `onJumpToHeading`（本文档的标题就是这张图的节点，所以 `#标题` 是找一个节点）。**锚点必须整段匹配**（忽略大小写）：**落在附近的链接比不跳更糟**，因为读者不会知道自己错过了。没有可用通道时，"打开"是**禁用并写明原因**，而不是消失 —— 会消失的控件什么也教不会。

**又一处 TDZ，这次的修法值得记**：我的"跟随链接"回调引用了**声明在它之后**的 `tree` 状态 → 整个组件崩，7 条 UI 测试同时失败。修法不是把那 60 行搬到后面，而是**把树作为显式入参**传进去（`handleOpenLink(tree, nodeId)`）—— 更少改动，也更清楚：这个函数需要什么，写在签名上。

**第三次"形状断言过期"之后，做了结构性修法**：那条"空伴生文件的键必须是这几项"的断言，每加一段就读一次错。改成断言**两个位置互相一致**（`Object.keys(emptySidecar())` ↔ `SIDECAR_SECTIONS`）—— 这才是真正要守的不变量；以后再加段落，测试不需要改，而"加了段落却忘了 `emptySidecar`"依然会被抓到。

### M3.6 完成：分支编号（**M3 六项到此全部完成**）

**一条边界决定了整个实现：编号是"画出来的"，不是"写进文字的"。** 树是要同步回文档的东西，把编号写进节点文字，就等于把读者从没打过的编号前缀塞进他的 Markdown；而且**节点框的宽高是布局引擎按文字量的**，编号混进文字就得混进测量，那正是黄金快照存在的意义。所以编号是**画在节点旁的小标签，不是文字的一部分** —— 测试里最能守住这条的是最后一条：**开着编号改一个节点并同步回文档，写出来的 Markdown 里没有任何编号**（三种可能形态都断言了）。

**画在左上角外侧**：这是唯一没被占的位置 —— 备注徽标在角上、标记在右上、图标在更左侧、标签在下方。也顺带绕开了"编号挤进框里会被裁掉或顶出去"的问题（3 级编号 `1.2.3` 比框的内边距宽）。

**编号只认文档结构，不认布局**：算编号的输入是**树**，不是布局结果 —— 所以**折叠分支、切换布局都不可能让编号变化**（函数压根不接收折叠集合，测试直接断言这点）。一条随"当时展开着什么"而变的编号，比没有编号更糟。

**开关按文档记在 localStorage**（与折叠、主题、布局同类），**这是对方案的一处偏离**：方案把编号列为"sidecar 开关"，但它决定的是"这张图怎么画"，而不是"文档带了什么" —— 这正是 sidecar 的界线；M0.7 的折叠也是同样的判断。代价相同：换台机器打开，丢的只是这个偏好。

**⚠️ 此处原本写的是"PNG / SVG 导出不带编号"—— 已订正（见下一节）**：导出拷贝的就是画布 DOM，编号本来就在文件里。

### 更正 + 完成：导出其实一直带着标注，缺的是颜色

**先纠正一处我说错、并且重复过多次的话。** 从 M3.1 起我反复讲"PNG / SVG 导出不带标注"，理由是"导出从布局数据重建"。**事实是：`buildStandaloneMindmapSvg` 拷贝的就是画布 DOM** —— 只剥掉选择框、加号、缩放手柄，再去掉平移缩放、解析节点与标题的填充（该函数 103 行，M2 之前就在）。所以**六种标注一直都在导出文件里**。这个结论我从未读那个函数就下了，而它一直是可以读的。

**真正的缺陷是颜色**：标注在屏幕上靠**样式表**上色，样式表不随文件走。于是实际导出效果是 —— 标签芯片**黑底黑字**（读不出来）、图标在深色节点上**整片黑**（看不见）、角标与编号是黑圆黑字。**画了，等于没画。**

**修法落在既有机制上**：构造器本来就为节点矩形、下划线、折叠圆、标题文字解析填充；现在补一张**声明式规则表**（选择器 → 暗/亮两套字面量 → 可选的字号字重），一次循环应用。**字号与字重也必须写出来** —— 它们同样只活在样式表里。

**为什么用字面量而不是 `getComputedStyle`**：屏幕上那些颜色是 `color-mix(… var(--surface-1))`，没有文档的样式表就求不出值；而且某个引擎算出的颜色记号（如 `color(srgb …)`）不一定被下一个打开文件的引擎认。这与构造器**既有的**节点填充做法一致，而且这里比那儿更站得住：**标注的颜色没有一项是读者可设的**，它们就是应用自己的强调色 —— 写下来是"抄录"，不是"猜"。

**两条新测试，一条管一头**：

1. **单元**：夹具里放上六种**不带任何颜色**的标注，断言导出后每一条都拿到了填充与字号，且**明暗两套值确实不同**（防"两套写成一样"的假通过）。
2. **组件**：真的渲染一张挂满标注的导图，再构建导出文件，断言六种标注**都在文件里**（含编号 `"1"`）—— 这条正是针对我先前那个错误结论，把"从布局数据重建"这条路彻底排除。

**顺带更正一处**：**PDF / 打印从来不是缺口** —— 它打印的就是渲染后的页面，标注与编号一直在。

**教训**：我把"导出不含标注"当作事实重复了五轮，从未打开那个 103 行的函数看一眼。**能读的代码不该靠推断下结论**；这次订正也说明记录的作用 —— 错话写在记录里，就还有被自己抓到的机会。

### M4 开始：关系线（4.2），以及它逼出来的一个真 bug

**先解释为什么不按编号做 4.1。** 4.1 自由主题需要**拖动 + 它自己的文本编辑 + 删除**三套交互；4.2 关系线的创建手势**直接复用已有的两主题 Ctrl 多选**（"对这两个做点什么"而不是"进入一个模式"）。所以关系线是 M4 里**最小的完整切片**。**自由主题紧随其后**，不是被放弃。

**规范对：无向，只存一种顺序。** `a→b` 与 `b→a` 是同一条关系 —— 否则同一条线会被存两次、画两次、只删掉一次。

**几何当作性质来测**：断言**任意两个框之间，两端都落在框边上**（而不只是举例）。理由与表盘几何一致 —— **一条从框内部开始的线看起来像是故意的**，肉眼查不出来。为此我又数错了一次（`M x y Q cx cy ex ey` 是 **6** 个数字，我按 8 个取了 `[6][7]`，取到 `undefined`）；现在的断言会**指名是哪一端不在框上**。这是这个批次里第三次"实现对、测试错"，且同样是**手数下标**。

**画在轮廓之下**（先于连线与节点绘制）且**虚线**：关系是对大纲的补充，实线同粗细会被读成大纲的一部分；`pointer-events: none` 保证它不抢平移与选中的点击。**一端不在画布上就不画这条线**（分支被折叠、标题被改名）—— 但**关系本身一个字也不动**（有测试）。

**导出带得上**：导出规则表为它扩展了「非颜色属性」（`fill: none`、虚线、线宽）—— 否则文件里会多出一个**黑色填充形状**。这是刚修完的那个坑的同一种。

#### ⚠️ 真正的收获：一个从 M3.1 就在的真 bug

写"连上 → 落盘 → 仍然有线"这条测试时发现：**线的状态被清掉了**。诊断（打印写入内容 vs 画面）给出的答案是：

- **写入的内容里有这条关系**（说明状态曾经正确），**画面却没有**；
- 根因：**伴生文件的读取是在编辑之后才落地的** —— `loadSidecar` 的 Promise 回来时执行 `setSidecar(loaded)`，把读者刚做的编辑**覆盖**成 `null`。

**真实后果比"线不见了"严重**：那一刻内存里只剩空文件，**紧接着的自动保存会把文件里其余的标注一起写没**。也就是说，**从 M3.1 起，只要读者在文件读完之前点一下图标/备注/标签，那次编辑会赢一瞬间，然后连同文件里原有的内容一起消失**。窗口只有几毫秒（一次 IPC 读小文件），但它是**丢数据**，不是显示问题。

**修法两头都保**：视图记录**读者碰过哪些段落**，迟到的装载改为**合并** —— `mergeSidecar(文件, 内存, 碰过的段落)`，**碰过的以读者为准、没碰过的以文件为准**。只看一边都会丢东西：丢掉编辑，或丢掉文件里其余全部。

**为什么以前没抓到**：这个 bug 只在"读取尚未落地时就有编辑"的时序下出现，而之前的组件测试都是**先等装载、再动手**（`waitFor` 或先 `settle`）—— 这条新测试是唯一一条**在同一 tick 里既编辑又推进计时器**的，于是把它撞了出来。**测试的时序覆盖不足，和没测是一样的。**

### M4.1 完成：自由主题（画布上的主题，文档不知道）

**决策 2 最纯粹的一次落地**：一个自由主题**只有 id、文字、坐标**，全部住在伴生文件里，**树与文档一个字都不动**。id 形如 `floating-1`，**递增而非随机** —— 同样的操作序列产生同样的文件，这在版本控制的知识库里意味着**可读的 diff**，也意味着这个特性可测。

**尺寸是量出来的，不是存下来的**：框的大小由 `calculateNodeDimensions` 按文字算 —— 改名就会重新成形，而文件里**永远不会存下一个与自身文字矛盾的尺寸**。测量用的是服务里那一份，所以自由主题和旁边的分支**看起来是同一套东西**。

**取景边界必须合并**：布局的边界**只知道树**（它从没听说过自由主题），所以导出、打印页与"适应画布"一律用 `unionBounds(布局边界, boundsOfBoxes(自由主题))` —— 否则**被拖到空白处的那一个，恰恰会从"本要展示它"的图里被裁掉**。这是附加层的必然代价，不是可选的优化。

**虚线成为统一的视觉语言**：关系线与自由主题都是虚线 —— 这个导图用"虚线"表示**"这是你加上去的那一层"**，与文档本身的实线相区分。

**选中状态是**分开的（`selectedFloatingId`，不混进 `selectedNodeIds`）：所有对"选中节点"生效的操作（删除、样式、连线、批量）都假定自己的 id 是节点，**只要有一个忘了这件事，就会作用于错误的对象**；多一份状态比逐个审计便宜。

**拖动监听在 window 上，落盘仍然防抖**：手势一旦开始，指针几乎立刻离开框体 —— **只在框内跟踪的拖动，会把手势丢在读者手离开形状的地方**。移动只写内存状态，文件照旧等那一次停顿（**一次拖动 = 一次写入**）。

**把文字清空即删除**：与段落读取器对"空主题"的判读**完全一致** —— 一处判读、一处实现，屏幕与后来的版本不可能对此有分歧。

**导出**：框与文字由规则表上色（否则文件里是黑框黑字），**选中圈被剥掉**（与节点选中圈同等对待：那是控件，不是画面）。

**这一版没做的**：自由主题**不承载备注/图标/标记/标签**。文件层面它们本来就能挂（那些都以 id 为键），但**面板是按节点做的**，没有地方编辑 —— 所以不画，而不是画了却改不了。这是明确的下一步，不是遗漏。

### M4.3 完成：概要（对一组主题加括号 + 一句说明）

**手势复用了已有的多选**：选中两个或更多主题 → 画布菜单一行"为本组加概要"。与关系线同一个入口、同一套选中，**没有新的模式要学** —— 后面的 4.4 边界也会用同一套。

**括号而不是方框**，这是刻意的：**方框围住一组节点就是"边界"（4.4）**，那是另一件事 —— 边界说的是"这些属于一起"，概要说的是"这一组加起来是这样"。两者可能同时出现在一张图上，**必须一眼分得开**。

**它有自己的 id（`summary-1`），与关系线不同**：关系线的身份就是那一对主题，而概要是可以被改名、被换掉跨度的 —— 这两种变化都不构成"另一个概要"。

**跨度按给定的记，不按范围记**：概要是关于**读者挑中的那几个主题**的。某个分支被移出这一组时，它带走的应该是**括号的含义**，而不是让括号悄悄改口。

**没有做的一项校验，及理由**：概要不检查所跨的主题**是否同级** —— 同级是它的正经用法，但**伴生文件模块里没有树，这是有意的**；为了校验一个手势而造一棵树，会把文件格式和布局耦合起来。因此跨度里某个主题不在画布上时（被折叠、被改名），括号就**按还在的那部分画**，全不在就不画。

**把标签清空不等于删除**（与自由主题相反）：自由主题的**文字就是它本身**，而概要里读者要的是**括号**；括号上没有字，它也仍然在说"这些是一组"。删除是它自己的动作。

**几何当作性质来测**：立在组的右侧、**高度恰好等于组高**、标签在括号之外并纵向居中 —— 与表盘同理，**偏两个像素的括号看起来像是故意的**，肉眼不会有人报。

**顺手做了一处结构收敛**：现在有三种东西会被行内编辑（节点文字、自由主题文字、概要标签），原来是两段并列的条件渲染 —— 改成**一个描述符 + 一个渲染点**，这也让"同时打开两个编辑器"从"不太可能"变成**不可能**。

**导出**：括号与标签由规则表上色（琥珀色，否则回来是黑线黑字），**选中框被剥掉**（与前两种一致：控件不是画面）。伴生文件至此**八段**，往返测试逐段断言。
