# KnowSpace · 工程规范与代码质量手册

> **面向**：所有向本仓库提交代码的人
> **性质**：可执行的约定，不是倡议。每一条都对应仓库里已经发生过的真实问题
> **维护**：新增规则时，必须同时写出「违反它会出什么事」

---

## 一、最重要的一条：一个概念只有一处定义

这个仓库最大的风险不是写得慢，而是**同一个概念被写了两遍，然后各自漂移**。历史上已经发生过多次，
`src/services/canvasTheme.ts` 的文件头就是一段事故记录：

> 屏幕渲染器和导出器各自维护了一份调色板，于是「浅色主题导出成了 `#f8fafc` 而不是用户看到的
> `#ffffff`，电子墨水主题导出成了近白而不是它的纸色，点阵网格从来就没对上过」。

所以，动手前先问自己：**这个知识，仓库里已经有地方存了吗？**

### 已有的单一事实来源（先查这里，再写新代码）

| 概念 | 唯一位置 |
| :--- | :--- |
| 画布配色（屏幕 + 导出共用） | `src/services/canvasTheme.ts` |
| 斜杠命令表、匹配、模板、触发规则 | `src/services/slashCommands.ts` |
| 卡片 Markdown 渲染 | `src/services/markdown.ts` |
| 白板数据结构与序列化 | `src/services/canvasSerialization.ts` |
| 弹窗通用样式令牌 | `src/components/canvas/canvasModalStyles.ts` |
| 闪念胶囊配色令牌 | `src/styles.css` 中 `.flash-capsule-overlay` 的 `--flash-*` 定义块 |
| 「系统主题」解析成具体主题 | `src/services/themeMode.ts` |
| 测试用例数权威口径 | `docs/TEST_BASELINE.md`（脚本生成，**禁止手改**） |
| 测试环境重置 | `src/__tests__/helpers/resetStores.ts` |

### 判定标准

- 同一个**规则**出现在两个文件里 → 抽出来，让两边调用它。
- 同一个**数字**（颜色、尺寸、阈值、用例数）出现在两个文件里 → 抽成常量。
- 两份实现「现在恰好一致」→ 视为已经不一致，因为没人会记得同步。

## 二、从历次修复中沉淀的九条规则

规则 1–6 出自 v2.6.3 之后「白板卡片斜杠命令」与「滚动清单带动画布」两处改动；
规则 7–8 出自闪念胶囊浅色主题的对比度修复。

### 规则 1：交互行为要抽成纯函数，而不是写在事件回调里

`detectSlashTrigger(text, caret)` 和 `canConsumeWheel(el, dx, dy)` 都是纯的：输入明确，输出明确，
不碰组件状态。带来三个好处——可单测、可复用、可读。

反例：把 `/` 的判定写成 `onChange` 里的一串正则，那么文档编辑器和白板卡片必然各写一份，
而两份一定会分叉。

### 规则 2：一个规则，两个消费者，才算「一样」

需求是「卡片里的 `/` 和文档编辑器一样」。做法不是**照抄一份 UI**，而是让两边调用同一个
`detectSlashTrigger`。照抄只能保证今天一样。

### 规则 3：变换层（transform）内部的浮层必须 portal 出去

卡片处在 `transform: translate3d(...) scale(...)` 的画布世界里。任何画在里面的弹层都会
**跟着被缩放和裁切**。所以卡片里的弹层一律：

- `createPortal(..., document.body)`
- 定位用 `position: fixed` + 屏幕坐标
- 配色读画布主题令牌，**不走全局 CSS**（全局 CSS 只认应用主题，画布有自己的一套主题）

### 规则 4：事件的归属要显式判定——判定器看得懂的交给它，看不懂的自己声明

先说清楚这一条**不是**「一律不许用 `stopPropagation`」。仓库里两种做法都在用，区别在于
**判定器能不能看懂这块区域**：

**交给 `services/wheelScrollGuard.ts` 的情况**：区域在画布 DOM 内部，而且它用滚轮做的事
**就是滚动**。此时判定器能回答「这个滚轮该归谁」，并且遵守浏览器的滚动链语义：
**内层还有得滚就归内层，滚到头就还给画布。** 卡片正文属于这种。

**必须自己 `stopPropagation` 的情况**，有两种，都不能指望判定器：

1. **区域被 portal 到 `document.body`。** 判定器是从事件目标**沿 DOM** 向上走到画布根；
   portal 出去的弹窗祖先链是 `menu → body → html`，永远走不到画布根，**对判定器不可见**。
   但事件仍然会到达画布的 `onWheel`——**React 传播走的是组件树，不是 DOM 树**。
   结果就是两边同时动：弹窗在滚，白板也在平移。
   （实例：`canvas/CanvasCardSuggestMenu`、白板右键菜单；`canvas/` 下其它四个弹窗一直是这么做的。）
2. **区域用滚轮做的是非滚动手势**，比如缩放。判定器的语义是「内层还有得滚就归内层」，
   它**没有能力表达**「这个区域为别的目的要这个滚轮」。一个 `overflow: visible` 的遮罩在
   它眼里就是"没得滚"，于是滚轮被交还给画布。
   （实例：`MediaLightbox` 用滚轮缩放，白板会在预览后面平移——关掉预览才发现漂了。）

> 反例仍然成立：**卡片正文不能无条件 `stopPropagation`**。卡片内容装得下时，滚轮应该继续
> 平移画布，无条件拦下来会让它变成死区。这正是判定器存在的理由。

**新增画布内浮层时的自查**：它是 portal 出去的吗？它用滚轮做的是滚动吗？两个问题里只要有
一个答案是「否」，就必须自己声明归属。

### 规则 5：测试要成对——「拦住」和「放行」各一条

只测「滚动卡片时画布不动」是不够的：如果代码把滚轮整个丢掉，这条测试**照样通过**。

所以必须补一条反向的：「卡片没得滚时，画布**要**动」。两条一起，才排除了假通过。

> 这条规则的通用形式：**任何「不要做某事」的断言，都要配一条「该做时确实做了」的断言。**
>
> 同一规则用在别处：媒体灯箱的滚轮测试同时断言**图片确实缩放了**（读数 100% → 115%）
> **且**白板没动——只断言「白板没动」的话，滚轮被谁都不处理时也会通过。

### 规则 6：注释写「为什么」，不写「做了什么」

```ts
// 差：遍历祖先元素，检查是否可滚动
// 好：内层还有得滚就归内层，滚到头就还给画布——否则滚轮停在卡片上就成了死区
```

代码本身说明了「做了什么」。注释唯一的价值是记录**当时为什么这么选**，
尤其是「不这么写会出什么事」。

### 规则 7：主题覆盖会盖掉状态类——状态必须自带主题变体

一条主题覆盖选择器天然比状态类多一层。`.flash-capsule-overlay.theme-light .flash-preset-tag`
是 (0,3,0)，而 `.flash-preset-tag.current` 只有 (0,2,0)——于是浅色主题下「当前预设」的
琥珀高亮被整条盖掉，看起来和没选中一样。这不是「覆盖写漏了」，是**写对了也照样被盖**。

**规则：给某个组件加了 `[data-theme=…]` / `.theme-…` 覆盖之后，必须同时检查它的全部状态类**
（`.active` / `.current` / `.pinned` / `.recording` / `:hover`），给每个状态补一条带主题前缀的规则。
仓库里 `.flash-tab-btn.active` 一直是这么写的，照它的样子办。

同一个坑的另外两种形态：

- **特异度相同不算「我赢」，源码顺序决定胜负。** `.flash-recorder-input.recording`（0,2,0）和
  `[data-theme="light"] .flash-recorder-input`（0,2,0）特异度一样，后者源码更靠后，
  于是浅色主题下录音态被整条抹掉，录制时没有任何视觉反馈。
- **主题块漏定义某个令牌时，属性会在计算值阶段变成 `unset`**——静默继承或回落初始值，
  比硬编码更难查（硬编码至少能在源码里搜到）。所以令牌必须在**基线块里全部给出值**，
  主题块只做覆盖，不做补充。

### 规则 8：颜色不靠眼睛判断，靠算

「这个颜色在浅色主题下有点淡」不是可执行的判据，而且开发时多半开着深色主题，肉眼根本看不出来。
把它换成 WCAG 2.1 的对比度比值（正文 4.5:1、图标 3:1），就变成一个**可以在 CI 里断言的数**。

闪念胶囊那 19 处漏覆盖就是这么暴露的：最低 1.48:1（`#cbd5e1` 配白水洗底）。
守卫测试在 `src/__tests__/flash-capsule-theme-contrast.test.ts`。它做三件事：

1. **从 `styles.css` 文本里按主题解析级联**——同一个控件往往有多条规则（基线、
   `.theme-light`、`[data-theme="light"]`、`:hover`），测试按 CSS 的逐属性级联
   （特异度 → 源码顺序）算出每条规则**实际生效**的前景色和底色。手写一张
   「令牌 ↔ 底色」对照表看着更直白，但它会随 CSS 改动过期，而**过期正是这个 bug 的成因**。
2. **自动收全待测选择器**：凡是声明了 `color` 的 `flash-` 规则都会被扫到——**包括硬编码 hex**，
   不只是 `var(--flash-*)`。只扫令牌会漏掉「写死了深色调、且没补主题覆盖」的规则。
   只改 `background`、颜色靠继承的 hover 态扫不到，显式列在 `EXTRA_SELECTORS` 里——
   它们恰恰是「令牌叠在更深淡色底上」的场景。
3. **范围由选择器决定，不能由「文件里的连续区块」决定。** 这是踩过的坑：原来按
   「从 `KnowSpace Flash Capsule` 注释切到 `Space Timeline` 注释」取范围，而 `flash-`
   规则在文件里有**两个**聚集区——主区块和 wikilink 下拉（约 8255~8353，物理上落在
   Knowledge Graph 区块里，是放错位置的 CSS）。第二段从来没被扫到，
   `.flash-wikilink-header .hint` 深色下 3.30:1、eink 下 `.flash-recorder-input` 2.17:1
   就是这么漏掉的。**CSS 会随手被追加到文件任意位置，按位置切片迟早漏。**
4. **底色不写死**：从容器底往上逐层叠（目录设置卡 / wikilink 下拉 → 控件自身淡色底），
   所以把 0.25 调成 0.4 会立刻变红。浮在胶囊**外面**的容器（`bottom: calc(100% + 4px)`）
   背后是桌面，基准底取白而不是胶囊面。

解析器本身也要防错——它错解会把「真失败」报成绿。所以另有一组断言钉住已知结果：
主题覆盖压过基线、hover 态的颜色继承基础规则、实色底取到具体颜色、特异度按**整条**
选择器算（只数最后一个复合选择器会丢掉 `.theme-eink` 的权重，报出不存在的失败——
这个 bug 真的写出来过）。

配套要求：**「达标」的断言必须配一条「不达标时确实会报」的断言**（见规则 5）。
这条测试里就是「改动前的 `#f59e0b` 在白底上确实 < 4.5」——否则阈值被改成永远通过也没人知道。

### 规则 9：主题必须只有一个决定点

`ThemeMode` 里有 `"system"`，而 CSS 里的主题覆盖是写在**具体主题**上的
（`.theme-light` / `[data-theme="light"]`）。把 `"system"` 直接当类名用，所有浅色规则
一条都匹配不到——而 `"system"` 是**默认值**，所以这条路径不是边缘情况，是主路径。

原来的补法是手工复制一组
`@media (prefers-color-scheme: light) { .flash-capsule-overlay.theme-system … }`，
只覆盖了容器和两个 textarea（面积大的控件），预设标签、徽章、小按钮、Tab 一个没补——
"跟随系统 + 浅色系统"的用户拿到白水洗底配 `#cbd5e1`（1.48:1）。

**规则：`"system"` 这类「间接取值」必须在渲染层解析成具体主题，不能让它流进 CSS。**
解析函数是 `src/services/themeMode.ts` 的 `resolveThemeMode()`，纯函数、可单测。

两个容易踩的细节：

- **解析结果必须同时用于类名和 `data-theme`。** 区块里的浅色覆盖一半写成
  `.flash-capsule-overlay.theme-light …`、一半写成 `[data-theme="light"] …`；只解析其中一个，
  另一族规则就会静默失效（`.flash-dir-label`、`.flash-starter-tag` 会退回 1.3~1.5:1）。
  胶囊是独立窗口，改它自己的 `data-theme` 不影响主窗口。
- **改前靠 CSS 媒体查询自动跟随系统，改成渲染层解析后必须自己监听 `matchMedia`**，
  否则用户切换系统主题时要重开窗口才生效。
- **解析前移会改变 `:root` 变量的生效集合，所以必须验证「被解析的那个窗口不消费全局变量」。**
  胶囊窗口的 `data-theme` 从 `"system"` 换成具体值之后，命中的 `:root[data-theme=…]` 规则
  就换了；它之所以零影响，靠的是两条结构事实：胶囊区块只读 `--flash-*`（零个全局变量），
  且没有任何非 flash 的 `[data-theme]` 规则能命中胶囊里的元素。这两条是**前提，不是显然成立**
  ——往胶囊里加一个全局类、或让它读一个全局变量，就会静默破坏它，而症状（某个主题下颜色变了）
  离那两行代码很远。守卫测试在 `src/__tests__/theme-mode.test.ts`。

区块内因此**不应再出现任何 `prefers-color-scheme` 规则**——守卫测试里有一条专门盯这个。

## 三、提交前门禁（四条，缺一不可）

```bash
npx tsc --noEmit                                  # 1. 类型必须干净
npx vitest run                                    # 2. 全量必须全绿
node scripts/capture-test-baseline.cjs            # 3. 改了用例数就重跑基线
git diff --stat docs/TEST_BASELINE.md             # 4. 确认用例数没有下降
```

**回归判定基线**（摘自 `docs/TEST_BASELINE.md`）：

1. 用例总数**不得低于**当前基线（删除测试必须在 PR 里论证）
2. 通过率 **100%**
3. 单个文件的用例数**不得下降**——这一条是为了防止测试被静默删除

## 四、测试卫生

### 4.1 偶发失败必须当 bug 修，不能靠重跑掩盖

「重跑一次就绿了」意味着这条测试**没有在保护任何东西**。它会在某次真实回归时恰好变绿，
让你以为改动是安全的。

**诊断手法**：如果单文件跑通过、全量跑失败，那是**状态泄漏**或**时序竞争**，
不是「环境问题」。

### 4.2 状态泄漏的两个来源

1. **`localStorage`**——组件持久化的偏好、进度、来源选择
2. **模块级单例**——zustand store 在 import 时创建，一个测试写的东西下一个测试还看得见

`beforeEach` 里必须清干净。仓库已经有统一入口 `src/__tests__/helpers/resetStores.ts`，
**新写的测试文件请直接用它**，不要自己手写清理逻辑。

### 4.3 一个真实案例

`daily-review-panel.test.tsx` 曾经有一个偶发失败：

- **症状**：全量跑时「头部显示待复习数量与进度」偶发失败，单文件跑 3/3 通过
- **根因**：`DailyReviewPanel` 会把「复习来源」写进 `localStorage`，而该文件的三个
  `beforeEach` 都没有清理存储。面板是在一个延迟步骤里落盘的，所以泄漏是否在下一个测试
  渲染前发生，取决于机器负载
- **为什么难查**：失败点和原因相隔十几个测试，且只在负载下复现
- **修复**：三个 `beforeEach` 各加一行 `localStorage.clear()`

**教训**：仓库里 8 个测试文件用了 `resetStores`，这个文件没用——**约定只要有一处不遵守，
它就不再是约定。**

### 4.4 超时预算是配置，不是默认值

`vitest.config.ts` 里必须显式写 `testTimeout`。默认的 5s 对本套件不够，而且它产生的失败现象
和真实回归**分不出来**：vitest 把超时报告成 `STACK_TRACE_ERROR`，于是一台忙的机器看起来像
坏掉的代码。

实测：`mindmap-marks-ui.test.tsx` 里一次面板交互就要 ~3.6s（空闲机器、已绕开沙箱的 fs 拦截层）
——重量级 jsdom 渲染 + 假定时器 + 真的往伴生文件写盘。某次负载下的全量跑挂了 7 个文件，
**全是超时，而每一个单文件跑都通过**；把预算放宽到 30s 后 1275 用例 0 失败。

**超时该用来抓「卡死」，不是抓「机器慢」。** 调这个值之前先量一遍最慢的用例。

> 顺带一提：`forks.singleFork: true` 让 103 个文件挤在同一个进程里顺序跑（全量约 200s）。
> 这是有意为之还是历史遗留，没人记得了。真要提速可以试着放开，但那是另一件事——先别顺手改。

### 4.5 墙钟性能断言要取多次，不要单次采样

`fsrs-service.test.ts` 里那条 `10000 次 currentRetrievability < 200ms`：空闲时约 130ms，
机器一忙 234ms。单次采样让它随负载时红时绿，红了也说不清是回归还是噪声。

正确做法是**预热 + 取 N 次里最快的一次，阈值和被测的循环一字不改**：

```ts
run();                                   // 热身：第一轮还在解释执行
const samples = [run(), run(), run()];
expect(Math.min(...samples)).toBeLessThan(200);
```

这样它抓的仍是数量级级别的回归（比如不小心写成 O(n²)），而不是 GC 或调度抖动。

**反例**：为了让它稳定就把阈值调大——那是掩盖，不是修。阈值是产品的验收标准，改它要产品说了算；
测量方法不是，测量方法只是工程。

## 五、打包与发布：环境陷阱与脚本前提

这一节的每一条都不是代码问题，但都会让人以为是代码问题，平均浪费一小时。

### 5.1 Electron 运行时下载会撞上 502

`electron-builder` 要下载 Electron 运行时。在挂了 HTTP 代理的机器上，这一步可能返回
`502 Bad Gateway`：

```
• packaging  platform=win32 arch=x64 electron=42.5.0 appOutDir=release\win-unpacked
⨯ Response code 502 (Bad Gateway)  failedTask=build
```

**别重试到天亮，也别怀疑自己改坏了。** 开发机上的 `node_modules/electron/dist/` 就是一份
完整的、已解包的 Electron 运行时（`electron .` 用的正是它），直接指过去：

```bash
npx electron-builder --win msi nsis dir \
  --config.electronDist="C:/Users/chunxvzhang/Desktop/codex/node_modules/electron/dist"
```

完全离线，而且更快。其余构建工具（wix / nsis / 7zip）已经在
`%LOCALAPPDATA%\electron-builder\Cache\` 里，不会再去下载。

### 5.2 便携目录删不掉，这是正常状态

`release/KnowSpace-win-x64` 同时是开发工作区，其中 `resources/app.asar` 被编辑器持有句柄：
**允许写入、拒绝改名与删除**（`EBUSY`）。不是权限问题，关掉编辑器也未必有用。

`scripts/package-desktop.cjs` 已经按这个前提写：先尝试清空目录（失败就失败），然后**合并式
复制**，最后比对内容——比对的是「这个目录是不是这次构建」，不是「这个目录是不是空的」。
一个文件可以既删不掉、又盖得掉，脚本利用的正是这一点。**不要"修"掉这个容错**，它是有意的。

### 5.3 差异比对只认 electron-builder 的产物

同一段比对还有一个前提：便携目录里本来就住着两类**不是**构建产物的东西——

- `.workbuddy-ai` / `.mimosa`：开发工作区的痕迹
- `docs/` / `assets/` / `release/` / `README.md`：第 4 步自己产出的便携版附加内容

它们由 `PORTABLE_ONLY_ENTRIES` 显式排除。**新增任何「不由 electron-builder 产生、却会出现在
便携目录里」的内容，必须同时加进这个集合**，否则它要么被当成"上一版残留"删掉，要么让比对
报错、打包在最后一步倒下。

同理，第 4 步只做加法，所以它在收尾处用 `pruneDirectory` 定向清理自己上一届的产物——否则
旧版本的安装包会一届一届攒进便携 zip（v2.6.0 的包里混着两个 v2.3.0 安装包就是这么来的）。

### 5.4 在 WorkBuddy 沙箱里打包：收尾删除会被拦，但产物已经写好

沙箱对单次批量删除有阈值（50 个文件/次）。electron-builder 在**产物写完之后**清理自己的临时
目录时会超阈值，于是构建报失败：

```
⨯ [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":341,"threshold":50,
   "targets":["...\release\__msi-x64"]}
    at StageDir.cleanup (app-builder-lib/src/targets/targetUtil.ts:16)
```

**关键是看产物在不在，而不是看退出码。** 上面这次失败时，`KnowSpace-2.6.4.msi` 和
`KnowSpace-Setup-2.6.4.exe` 都已经生成并签名完毕。判据：

```bash
ls -la release/KnowSpace-2.6.4.msi release/KnowSpace-Setup-2.6.4.exe
# MSI 用 OLE 头校验：前 8 字节应为 d0cf11e0a1b11ae1
```

**阈值是按「一次请求」累计的**，不是按单次调用：同一回合里所有工具调用的删除量加在一起算 50 个
文件，被拦下的尝试不消耗额度。所以别指望"分几次删"能绕过去——那是刻意设计的。

还有一种更麻烦的情况：沙箱里回收站后端可能不可用，此时 shim 是 **fail-closed（拒绝删除）**，
于是**任何删除都失败**。这正是 `pruneDirectory` 原来那个 `.catch(() => {})` 藏住的坑——清理
根本没做成，症状却是"便携 zip 里莫名多出上一版的安装包"。现在它会打印
`[warn] stale entry kept: <path> (<reason>)`。**见到这行就去查删除为什么失败，别当没看见。**

### 5.5 只同步、不重打包

安装包已经构建好、只想更新便携目录或重打 zip：

```bash
node scripts/package-desktop.cjs --skip-builder
```

跳过 electron-builder。它慢，而且每次都会先清空 `release/win-unpacked` 和自己的暂存目录——
只想同步的时候那两件事都是白做的。

### 5.6 推送：网络与凭据是两个独立的坑，别把它们混成一个

发版最后一步是 `git push`。它有两种失败，**排查方向完全相反**，所以先分清是哪一种。

**坑一：`github.com` 只能走本地代理，而且端口不是文档默认值。**

`github.com` 在这台网络下直连不通（表现为 20 秒超时后
`Failed to connect to github.com port 443`）。可用的代理端口是 **`7897`**——
文档里常写的 `7890` 在这里并没有监听。用 `scripts/push.ps1`，它按候选端口逐个探测：

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/push.ps1
```

**坑二：代理对了，但 git 读的不是你设的那个变量。**

这是最容易误判的一处。`push.ps1` 原先只设 `HTTPS_PROXY` / `HTTP_PROXY`（大写），
而 git 走 libcurl，**libcurl 优先读小写 `https_proxy`**。环境里一旦已经存在小写那份
（代理软件导出的、包装脚本留下的、上次实验忘了清的），大写变量就被完全忽略，push 走了
另一个代理，然后失败——报 `Empty reply from server`，或者一个根本没被要求承载这份流量的
代理回 `502`。**这看起来像网络故障，其实是变量优先级问题。** 脚本已改为四个变量同设，
并在找不到代理时显式清掉四个（否则"直连"并没有在直连）。

> 同理：**curl 的 `-x` 优先级高于环境变量**。所以
> `curl -x http://127.0.0.1:7897 https://github.com` 返回 200、而 `git push` 仍报 502 是
> 完全可能的——两者读的不是同一处配置。判"某主机是否可达"必须**用同一个客户端**测。

**坑三：凭据助手需要交互式桌面会话。**

如果 push 卡住约 30 秒、最后报 `could not read Username ... terminal prompts disabled`，
那代理是好的，问题在凭据：`git credential fill` 取不到账号。这台机器上的 git 是
**WorkBuddy 自带的 PortableGit**（`credential.helper=helper-selector` → `manager`），
凭据助手要读交互式桌面会话，在 agent 会话里取不到。SSH 路线也不通（没有 `~/.ssh`，
`ssh.github.com:443` 走代理也不可达）。

> **`ls-remote` 成功不代表鉴权正常。** 公开仓库的读操作不需要凭据，所以
> `git ls-remote origin` 会漂亮地成功，而紧接着的 `git push` 卡在凭据上。
> 别把前者当成"鉴权没问题"的证据。

**结论：推送这一步由人在普通终端里执行。** agent 会话可以完成到提交为止，但不要为了
"走通"去改 remote 地址、把 token 写进命令或配置文件——那会把一个环境限制变成一份凭据泄漏。

## 七、Code Review 检查清单

提交者自查、评审者对照：

- [ ] 新增的规则/数字，仓库里是否已有唯一来源？是否复用了它？
- [ ] 纯逻辑是否抽成了可单测的函数，而不是埋在事件回调里？
- [ ] 浮层是否在 transform 容器内？是否 portal + fixed + 主题令牌？
- [ ] 新增/改动了画布内的浮层？**它是 portal 出去的吗？它用滚轮做的是滚动吗？** 任一为「否」
      就必须自己 `stopPropagation`（规则 4）；判定器看不到 portal，也看不懂非滚动手势。
- [ ] 「不要做某事」的测试，是否配了「该做时确实做了」的反向断言？
- [ ] 给组件加了主题覆盖（`[data-theme=…]` / `.theme-…`）？**它的每个状态类都补了主题变体吗？**
      （规则 7：`.active` / `.current` / `.pinned` / `.recording` / `:hover`；注意特异度相同的情况下
      源码顺序也决定胜负）
- [ ] 新增了颜色令牌？**基线块里给出值了吗？**主题块只做覆盖——漏定义会变成 `unset` 静默回落。
- [ ] 新增/改了颜色？**对比度算过吗**（正文 4.5:1、图标 3:1）？配套的守卫测试是否读的是
      CSS 文本而不是复制一份常量？（规则 8）
- [ ] 新样式挂在某个主题上？**这个主题是「间接取值」吗**（`"system"` 这类需要先解析的）？
      是的话必须在渲染层解析成具体主题，并且解析结果要同时用于类名和 `data-theme`（规则 9）。
- [ ] 注释是否在解释「为什么」，而不是复述代码？
- [ ] `tsc --noEmit` 干净、`vitest run` 全绿、用例数未下降？
- [ ] 是否引入了新的 `beforeEach` 状态，而没有清理？
